# Invite-Link Authentication

## Overview

Authentication is based on long-lived sessions created through single-use invite links. There are no passwords, no email addresses, and no external identity providers. Access to the application is controlled entirely through the invite mechanism: only an authenticated user can generate an invite link, and only a valid invite link can create a new session.

## Sessions

Each session is a server-side record associating a session ID with a user ID. The session ID is stored in an httponly cookie with a sliding 30-day expiration, renewed on each request. A user remains logged in as long as they use the application at least once within any 30-day window.

## Invite Links

An invite link contains a single-use token. Tokens are stored server-side with metadata: who created them, when, when they expire, and optionally which user they are for.

There are two kinds of invite:

- **New user invite.** The token has no associated user ID. When consumed, the application presents an identity selection or creation flow, then creates a session for the chosen user.
- **Self-invite (device transfer).** The token is pre-associated with the generating user's ID. When consumed, the application creates a session for that user immediately, with no identity selection step.

Both types use the same token table and the same consuming endpoint. The only difference is whether the user ID field on the token is populated.

## Recovery Codes

When a user's session is first created, the server generates a single-use recovery code (8-12 alphanumeric characters) and displays it once. The server stores a hash of this code alongside the user record.

If a user loses their session and cannot obtain a new invite link, they can enter their recovery code at a recovery endpoint. The server validates the code, creates a new session, invalidates the old code, and generates and displays a new one.

Recovery codes are a convenience path. The fallback for a user who has lost both their session and their recovery code is to receive a new invite link from another authenticated user.

## Access Control

The system is closed by design. There is no public registration. The only entry points are invite links generated by existing users or an administrator. Revoking access is done by deleting a user's sessions from the server-side session store.
